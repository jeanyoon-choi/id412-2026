## 1. 모바일 모달리티 & 파라메트릭 인터페이스 [#1-mobile-modality--parametric-interface]

**모바일 모달리티: 모바일이라는 악기**

- 영화 "2001: 스페이스 오디세이"의 유명한 장면에서는 뼈가 인공위성으로 바뀐다. 도구의 진화를 보여주는 장면이다.
  - [2001: A Space Odyssey (1968) - From Bone to Satellite Scene (1/6) | Movieclips](https://www.youtube.com/watch?v=avjdKTqiVvQ)
- 2007년 스티브 잡스가 아이폰을 발표한 순간도 비슷했다. 강력한 새 도구가 우리 손에 들어왔다.
  - [Steve Jobs introduces iPhone in 2007](https://youtu.be/MnrJzXM7a6o?si=eriyVK-ald9RRGN9&t=274)
- 우리가 가진 가장 좋은 도구는 손가락이다. 아이폰/스마트폰은 손가락으로 연주하는 악기다.
- **목표**: 이 "연주"에 반응하는 인터페이스 만들기.
  - 악기 같은 인터페이스 (Instrumental Interface)

**인터랙션의 두 종류**

- **1. 의미적 인터랙션 (Semantic, 의미 기반)**
  - **특징**: 불연속적이고 범주가 나뉘어 있다. 하나를 분명하게 고른다.
  - **예**: 버튼 클릭, 메뉴에서 옵션 선택.
  - **쓰이는 곳**: 실용적인 인터페이스 대부분 (앱, 웹사이트).
- **2. 현상학적 인터랙션 (Phenomenological, 경험 기반)**
  - **특징**: 연속적이고 끊김 없이 이어진다.
  - **예**: 몸 움직이기, 손가락으로 드래그하기, 스크롤.
  - **쓰이는 곳**: 인터랙티브 아트, 게임.
**파라메트릭 웹 인터페이스**

- **무엇인가?** 모바일에서의 인터랙션(입력)으로 _파라미터_(변수)를 바꾸는 인터페이스.
- 악기 연주를 떠올리면 된다. 악기에서는 동작이 소리를 바꾼다. 여기서는 동작이 *맥락*, *시간*, *공간*을 바꾼다.
- **예: 시간 바꾸기**
  - _의미적 방식_: 입력칸에 "8:00 AM"을 적는다.
  - _현상학적 방식_: iOS 알람처럼 다이얼을 돌린다. (iOS 휠 피커 - 라스베이거스에서 영감을 얻었다)
  - _질문_: 어느 쪽이 더 직관적인가? 어느 쪽이 더 재미있는가?
- **예: 계절 바꾸기**
  - _의미적 방식_: 따로 떨어진 버튼 4개 ("봄", "여름", "가을", "겨울").
  - _현상학적 방식_: X축이나 Y축 슬라이더 하나. 움직이면 계절이 끊김 없이 섞이며 넘어간다.
- **예: 직업 바꾸기**
  - _의미적 방식_: 미리 정해둔 직업이 나열된 드롭다운.
  - _현상학적 방식_: 경계가 "흐릿한" 선택 공간. 여러 직업군 사이를 미끄러지듯 오간다.

**입력 재료 (악기의 "건반")**

- **I. 선택 / 내비게이션 (대략적인 조작)**
  - 스크롤
  - 스와이프 (예: 틴더처럼 카드 넘기기)
  - 줌 인 / 줌 아웃
- **II. 미세 조정 (정밀한 조작)**
  - 핑거 스케이팅 / 스케치 (화면에 그리기)
  - 토글 여러 개 (on/off 스위치)
  - 슬라이더 여러 개
  - 버튼 여러 개
  - 가속도계 (모바일 기울이기)
  - 음성/말
    - _의미적_: Speech-to-Text (무슨 말을 하는가)
    - _비의미적_: 음량 (얼마나 크게 말하는가)
  - 카메라 트래킹 (시선 추적, 사물 인식)
  - 오브젝트 회전 & 확대/축소

## 3. Socket.io [#3-socketio]

- <Term id="websocket" />: 클라이언트와 서버가 실시간으로 양방향 통신하는 방식. 웹에서 기기끼리 실시간으로 인터랙션할 수 있게 해준다
- <Term id="socketio" />: WebSocket을 쓰기 쉽게 감싼 Javascript 라이브러리. 입문자가 쓰기 좋다 (자동 재연결, fallback 기본 제공)
- 방식
  - 클라이언트 A(인터랙션 입력)와 클라이언트 B(인터랙션 출력)가 있다고 하자
  - 클라이언트 A가 메시지를 보낸다 → relay 서버가 같은 room에 있는 나머지 클라이언트 모두에게 전달한다 → 클라이언트 B가 받는다
- 템플릿에 이미 설치되어 있다: `socket.io` (서버), `socket.io-client` (브라우저)

<SocketDiagram />

**이 레포에서의 구조**

- `socket-server.mjs`: relay 서버. 파일 하나로 되어 있고 4000번 포트를 쓴다
  - `join(room)`: 기기가 room에 들어간다
  - `message({ type, data })`: 같은 room에 있는 나머지 기기 모두에게 그대로 전달된다
  - Next.js에 포함된 것이 아니라 따로 실행되는 Node 프로세스다 (그래서 Vercel에는 올릴 수 없다. [§7](#7-socket-deployment) 참고)
- `hooks/shared/useSocket.ts`: 클라이언트 쪽 hook
  - `const { send, connected } = useSocket(room, onMessage)`
  - `send(type, data)`: room에 메시지를 보낸다
  - `onMessage(type, data)`: 다른 기기에서 메시지가 올 때마다 호출된다
  - 주소: `NEXT_PUBLIC_SOCKET_URL`이 설정되어 있으면 그 주소, 없으면 현재 호스트의 4000번 포트
- 실험 하나의 라우트 구성 규칙
  - 두 페이지 모두 같은 room 이름으로 `useSocket("<name>", ...)`을 호출한다

  | | 파일 | 주소 |
  |---|---|---|
  | 클라이언트 A · 모바일 | `app/experiments/w2/<name>/mobile/page.tsx` | localhost:3000/experiments/w2/name/mobile |
  | 클라이언트 B · 스크린 | `app/experiments/w2/<name>/screen/page.tsx` | localhost:3000/experiments/w2/name/screen |

**전체 흐름**

다이어그램의 번호 다섯 개는 다음과 같다.

1. 스크린 페이지를 연다. `useSocket("drawing", onMessage)`가 relay에 연결하고 room에 들어간다
2. 모바일 페이지를 연다. 스크린과 마찬가지다
3. 모바일: `send("move", { x, y })`
4. Relay: `{ type: "move", data: { x, y } }`를 room의 나머지 기기에 전달한다
5. 스크린: `onMessage("move", { x, y })`가 호출된다. state를 업데이트하고 화면에 그린다

- 여기까지가 기본 코드다. 이 위에 더 복잡한 기능을 얹거나 모듈로 나눠도 된다
- 기기 사이에 어떤 사변적(speculative) 인터랙션을 만들 것인가? 이 기술을 인터랙티브/몰입형 오디오비주얼 디자인 작업에 어떻게 쓸 것인가?
- Socket.io/WebSocket은 TouchDesigner나 Unreal과도 연결할 수 있다 (W3)

## 5. 모바일 HTTPS 디버깅 [#5-mobile-https-debugging]

- 모바일 디버깅: 어렵다
- 크로스 디바이스 (모바일 + 데스크톱) 디버깅: 훨씬 더 어렵다

### A1. 로컬 네트워크로 접속하기 [#a1-local-network-connection]

노트북에서 띄운 페이지를 모바일에서 연다. `pnpm dev`는 계속 켜둔다.

- `localhost`는 "지금 이 기기"를 뜻한다. 노트북에서 localhost:3000은 노트북을 가리킨다. 모바일에서 localhost를 입력하면 모바일 자신을 가리키는데, 모바일에서는 아무것도 실행되고 있지 않다
- 그래서 모바일에는 같은 Wi-Fi 안에서 노트북을 가리키는 주소, 즉 IP 주소가 필요하다. IP 주소는 Wi-Fi 공유기가 기기마다 하나씩 나눠준다. 192.168.0.12나 10.0.0.12 같은 형태다
- 노트북의 IP 주소를 찾는 방법은 두 가지다
  1. 터미널에서 찾기
     - **macOS** 또는 **Linux**: `ifconfig | grep "inet "`
     - **Windows**: `ipconfig`
     - 192.168.x.x나 10.x.x.x 형태의 주소를 쓴다. 127.0.0.1은 localhost이므로 아니다
  2. AI 에이전트에게 묻기: "내 컴퓨터의 로컬 IP 주소가 뭐야?" 에이전트가 명령어를 실행해서 알려준다
- 모바일과 노트북을 **같은 Wi-Fi**에 연결한다. 학교 Wi-Fi가 기기끼리의 통신을 막고 있으면 모바일 핫스팟을 쓴다
- 모바일 브라우저에 `http://<YOUR_IP>:3000`과 경로를 입력한다. 예: http://192.168.0.12:3000/experiments/w2/drawing/mobile
- 노트북에서는 평소처럼 스크린 페이지를 연다: localhost:3000/experiments/w2/drawing/screen

### A2. 로컬 개발용 <Term id="https">HTTPS</Term>: `pnpm dev:mobile` [#a2-https-for-local-dev-pnpm-devmobile]

**왜 HTTPS가 필요한가**

- `http://`: 페이지와 브라우저가 주고받는 내용이 암호화되지 않는다. 같은 네트워크에 있으면 누구나 읽을 수 있다
- `https://`: 내용이 암호화된다. 페이지와 브라우저만 읽을 수 있다
- 카메라, 마이크, 모션 센서에는 사용자의 모습과 지금 있는 공간이 그대로 담긴다. 그래서 브라우저는 `https://`로 연 페이지에서만 이 기능을 쓰게 해준다
- 예외가 하나 있다. `localhost`다. localhost에서는 아무것도 내 기기 밖으로 나가지 않는다. W1에서 `pnpm dev`만으로 노트북 카메라를 쓸 수 있었던 이유다
- 모바일은 `http://192.168.x.x`로 페이지를 연다. localhost도 아니고 https도 아니다. 그래서 페이지를 https로 띄우기 전까지는 카메라와 센서가 막힌다

**방법**

1. 실행 중인 서버를 끈다. `pnpm dev`를 실행한 터미널에서 `Ctrl + C`를 누른다
2. `pnpm dev:mobile`로 다시 켠다. 서버 두 개(3000, 4000)는 그대로이고 이번에는 https로 뜬다. 처음 실행할 때는 비밀번호를 물어볼 수 있다. 모바일에서 열 주소가 출력된다
3. 모바일에서 `https://<YOUR_IP>:3000`과 경로를 연다. 경고 페이지가 뜬다 ("연결이 비공개로 설정되어 있지 않습니다")
   - **정상**이다. 인증서는 "이 사이트가 진짜 그 사이트가 맞다"는 것을 증명하는데, 이 인증서를 내 노트북이 직접 만들었기 때문에 모바일이 확인할 수 없다
   - **"고급"** → **"계속 진행 (안전하지 않음)"**을 누른다
4. relay도 똑같이 해준다. 모바일에서 `https://<YOUR_IP>:4000`을 열고 경고를 넘어간다. "socket relay ok"가 보여야 한다
   - 이 단계를 건너뛰면 페이지는 열리지만 스크린에는 아무것도 전달되지 않는다
5. 노트북에서는 https://localhost:3000을 연다

경고는 기기마다 한 번만 넘어가면 된다.

### A3. 원격 디버깅 (iOS vs. Android) [#a3-remote-debugging-ios-vs-android]

모바일의 console.log() 메시지, DOM, 네트워크 요청을 컴퓨터 화면에서 확인한다.

#### Android (Chrome 디버깅) [#android-chrome-debugging]

1. **Android 기기에서:** "개발자 옵션"을 켠다 (보통 숨겨져 있으므로 본인 기종에서 켜는 방법을 검색한다). 개발자 옵션에서 "USB 디버깅"을 켠다.
2. **컴퓨터에서:** 모바일을 USB 케이블로 컴퓨터에 연결한다.
3. 데스크톱 **Chrome**을 열고 주소창에 `chrome://inspect#devices`를 입력한다.
4. 연결한 기기와 열려 있는 탭이 보인다. 디버깅할 탭의 "Inspect"를 누른다.
5. DevTools 창이 열리고, 모바일 브라우저를 여기서 검사할 수 있다.

#### iOS (Safari Web Inspector)

**참고:** **Mac**이 있어야 한다.

1. **iPhone에서:** 설정 > Safari > 고급으로 들어가 "웹 속성(Web Inspector)"을 켠다.
2. **Mac에서:** **Safari**를 연다. Safari > 설정 > 고급으로 들어가 맨 아래의 "메뉴 막대에서 개발자용 메뉴 보기"를 체크한다.
3. **연결:** iPhone을 USB 케이블로 Mac에 연결한다.
4. Mac의 Safari에 새로 생긴 "개발자용" 메뉴를 누른다. iPhone 이름이 보인다.
5. iPhone 이름에 마우스를 올리면 열려 있는 탭 목록이 나온다. 디버깅할 탭을 누르면 Web Inspector 창이 열린다.

## 6. 모바일 센서 [#6-mobile-sensors]

- 카메라, 마이크, 모션 센서는 <Term id="https">HTTPS</Term>(또는 localhost)에서만 작동한다: `pnpm dev:mobile` ([A2](#a2-https-for-local-dev-pnpm-devmobile))
- 사용자가 탭한 뒤에 시작된다. 브라우저가 권한을 묻는다

| | 입력 | 브라우저 API | 예제 |
| --- | --- | --- | --- |
| <SensorMotion kind="tilt" /> | 기울기 | `deviceorientation` 이벤트 → `alpha`, `beta`, `gamma` (도) | [w2/tilt](/experiments/w2/tilt/screen) |
| <SensorMotion kind="shake" /> | 흔들기 | `devicemotion` 이벤트 → `acceleration` | |
| <SensorMotion kind="microphone" /> | 마이크 | `navigator.mediaDevices.getUserMedia({ audio: true })` | [w1/video](/experiments/w1/video) |
| <SensorMotion kind="camera" /> | 카메라 | `navigator.mediaDevices.getUserMedia({ video: true })` | [w2/camera-slit-scan](/experiments/w2/camera-slit-scan/screen) · [w1/glsl/creation-webcam](/experiments/w1/glsl/creation-webcam) |

**기울기 (가속도계)**

- iOS: 탭 핸들러 안에서 `DeviceOrientationEvent.requestPermission()`을 호출한다. Android: 권한 팝업이 없다

```tsx
async function start() {
  // iOS만: 권한 요청 (탭 안에서 불러야 한다)
  const eventClass = DeviceOrientationEvent as unknown as { requestPermission?: () => Promise<string> };
  if (eventClass.requestPermission) await eventClass.requestPermission();

  window.addEventListener("deviceorientation", (event) => {
    const x = (event.gamma ?? 0) / 45; // 좌 / 우
    const y = (event.beta ?? 0) / 45; // 앞 / 뒤
    send("tilt", { x, y });
  });
}
```

- 전체 코드: `app/experiments/w2/tilt/`

**예제 (HTTPS)**

1. Tilt: 모바일 기울기 → 스크린의 공 ([mobile](/experiments/w2/tilt/mobile) · [screen](/experiments/w2/tilt/screen))
2. Camera Slit-Scan: 모바일 카메라 → 스크린의 슬릿 스캔 ([mobile](/experiments/w2/camera-slit-scan/mobile) · [screen](/experiments/w2/camera-slit-scan/screen))

## 7. Socket 배포 [#7-socket-deployment]

- [W1 §12](/lecture-materials/w1#12-deployment)에서 한 배포는 내 노트북(localhost)에서만 열리던 앱을 <Term id="vercel" />에 올려서 누구나 접속할 수 있게 만드는 일이었다
- 멀티 디바이스 작업은 프로그램 두 개가 같이 돌아야 한다([§3](#3-socketio)). Next.js 앱(3000 포트)과 relay 서버 `socket-server.mjs`(4000 포트)다
- 이 중에서 Vercel에 올릴 수 있는 것은 Next.js 앱뿐이다. relay 서버는 올릴 수 없다
  - Vercel은 serverless 방식이라, 누군가 페이지를 열 때만 잠깐 코드를 실행하고 곧바로 종료한다
  - 반면 relay 서버는 모바일, 스크린과 연결을 계속 유지해야 해서 꺼지면 안 된다
- 따라서 relay 서버를 계속 켜둘 컴퓨터가 따로 있어야 한다. 방법은 두 가지다

**1. 내 노트북에서 돌리기**

- 수업 시간에 쓴 방식이다. `pnpm dev`(또는 `pnpm dev:mobile`)를 실행하면 두 프로그램이 노트북에서 함께 돌고, 모바일은 같은 Wi-Fi로 접속한다([§5](#5-mobile-https-debugging))
- 따로 배포할 필요는 없지만, 같은 Wi-Fi에 연결된 기기에서만 열린다

**2. 인터넷 서버에 올리기**

- Next.js 앱은 W1 때처럼 Vercel에 올리고, relay 서버는 프로그램을 계속 켜둘 수 있는 호스팅 서비스에 올린다. <Term id="render" />나 <Term id="railway" />를 쓴다
  - <Term id="ec2" />도 한 예다. 반포자이즘의 relay 서버가 여기서 돌아간다
- 이렇게 하면 같은 Wi-Fi가 아니어도, 주소만 알면 어디서든 작업을 열 수 있다
- Black Room에서 진행하는 기말 프로젝트는 이 방식으로 배포하기를 권장한다

**앱에 relay 서버 주소 알려주기**

- 노트북에서는 앱과 relay 서버가 같은 컴퓨터에 있었다. 그래서 주소를 따로 알려주지 않아도 페이지가 "지금 이 컴퓨터의 4000 포트"로 접속하면 됐다
- 배포하고 나면 둘이 서로 다른 곳에 있게 된다. 앱은 Vercel에, relay 서버는 Render에 있고 주소도 각각 다르다. 앱은 relay 서버가 어디에 있는지 모르기 때문에 주소를 직접 알려줘야 한다
- 주소는 Vercel의 환경 변수(Environment Variable)로 알려준다. 환경 변수는 코드에 직접 적지 않는 값이다. 서비스의 설정 화면에 "이름 = 값" 형태로 적어두면 앱이 그 값을 읽어서 쓴다
  - 이름: `NEXT_PUBLIC_SOCKET_URL`. 이 템플릿의 `useSocket`은 이 이름으로 relay 서버 주소를 찾는다
  - 값: Render가 만들어 준 relay 서버 주소. 예를 들면 `https://my-relay.onrender.com`

**Render로 배포하기**

1. Next.js 앱: 레포를 GitHub에 push한 뒤 Vercel에 배포한다 ([W1 §12](/lecture-materials/w1#12-deployment))
2. relay 서버: https://render.com → 가입 → **+ New > Web Service** → 앱을 올린 것과 같은 GitHub 레포 선택 → **Connect**
3. 설정 항목을 아래와 같이 입력한다. Start Command에 적은 명령 때문에 이 서비스는 Next.js 앱이 아니라 relay 서버를 실행하게 된다
   - Language: `Node`
   - Build Command: `pnpm install`
   - Start Command: `node socket-server.mjs`
   - Compute: `Free`
   - Environment Variables: `NODE_VERSION` = `24`
4. 배포가 끝나면 Render가 relay 서버의 주소(`https://<name>.onrender.com`)를 만들어 준다. 이 주소를 열었을 때 "socket relay ok"가 보이면 정상이다
5. 이 주소를 Vercel에 환경 변수로 등록한다
   - Vercel에서 내 프로젝트를 연다 → **Settings** → **Environment Variables**
   - Key에 `NEXT_PUBLIC_SOCKET_URL`, Value에 `https://<name>.onrender.com`을 입력하고 **Save**를 누른다
   - 다시 배포한다. **Deployments** → 가장 최근 배포의 **⋯** → **Redeploy**. 환경 변수는 배포할 때 앱에 들어가기 때문에, 다시 배포해야 적용된다
6. Vercel 주소로 접속해서 노트북에서는 `/screen`, 모바일에서는 `/mobile`을 연다

- 무료 플랜에서는 15분 동안 접속이 없으면 relay 서버가 꺼진다. 그 뒤 처음 접속할 때는 다시 켜지느라 1분 정도 걸린다
- 문서: [Your first deploy](https://render.com/docs/your-first-deploy) · [WebSockets](https://render.com/docs/websocket) · [Free plan](https://render.com/docs/free)

**Railway로 배포하기**

1. Next.js 앱: 위와 똑같이 Vercel에 배포한다
2. relay 서버: https://railway.com → GitHub 계정으로 가입 → **New Project** → **GitHub repo** → 같은 레포 선택
3. 서비스 → **Settings** → Custom Start Command에 `node socket-server.mjs` 입력 → **Deploy**
4. 서비스 → **Settings** → **Networking** → **Generate Domain**. 만들어진 주소 `https://<name>.up.railway.app`을 열었을 때 "socket relay ok"가 보이면 정상이다
5. 이 주소를 Vercel에 환경 변수로 등록한다. 위 5번과 같고, Railway 주소를 넣으면 된다

- 무료 체험은 크레딧 $5, 30일까지다. 그 이후에는 월 $5를 낸다
- 문서: [Quick start](https://docs.railway.com/quick-start) · [Build and start commands](https://docs.railway.com/builds/build-and-start-commands) · [Domains](https://docs.railway.com/networking/domains/working-with-domains)
