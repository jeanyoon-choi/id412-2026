## 2. The Frontend Landscape

Where the tools we use sit, so that tutorials, job posts and agents' suggestions make sense.

- Fundamentals: <Term id="html" />, <Term id="css" />, <Term id="javascript" />. Everything below compiles down to these three
- Language on top: <Term id="typescript" />. Javascript with types. What the industry writes now
- UI frameworks (component model, state → view)
  - <Term id="react" /> (Meta) — the standard. What we use
  - [Vue](https://vuejs.org/), [Svelte](https://svelte.dev/), [Angular](https://angular.dev/) — same job, different syntax and philosophy
- Meta-frameworks (routing, server, build on top of a UI framework)
  - <Term id="nextjs" /> (Vercel, on React) — what we use
  - [React Router / Remix](https://reactrouter.com/), [Astro](https://astro.build/), [Nuxt](https://nuxt.com/) (Vue), [SvelteKit](https://svelte.dev/docs/kit) (Svelte)
- Styling
  - <Term id="cssModules" /> — what we use. Plain CSS, scoped per file
  - [Tailwind](https://tailwindcss.com/) (utility classes), [styled-components](https://styled-components.com/) (CSS-in-JS), [Sass](https://sass-lang.com/)
- Runtime and packages (our pipeline)
  - [Node.js](https://nodejs.org/) runs Javascript outside the browser. It is what `pnpm dev` and the socket relay run on
  - Packages come from the [npm registry](https://www.npmjs.com/); <Term id="npm" />, <Term id="yarn" /> and <Term id="pnpm" /> are three tools that install from it. We use pnpm
- Creative layers on top of all this
  - <Term id="canvas" /> and [SVG](https://developer.mozilla.org/en-US/docs/Web/SVG) for 2D, [p5.js](https://p5js.org/) as the art-school wrapper
  - [WebGL](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API) and [WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API) for the GPU, <Term id="threejs" /> on top, <Term id="glsl" /> inside
  - <Term id="webAudio" /> for sound, <Term id="websocket" /> for real-time

## 7. How We Work in Class

- I don't hand out code. We open Claude Code together and build each experiment live, from an empty folder. You do the same on your laptop, at the same time
- Why: the point is not the code. It is the loop. Describe → agent builds → look → say what's wrong → repeat. You learn the loop by doing it, not by reading a finished file
- One experiment = one folder: `app/experiments/w1/<kebab-name>/`. Name it after what it does (`time-interval`, `mouse-trail`), not `test1`
  - `page.tsx` (+ `page.module.css`) inside. Helpers next to it. Assets in `public/experiments/w1/<kebab-name>/`
  - The agent writes a short `README.md` in the folder: what it is, inputs, parameters, how to run. The rules are in `docs/experiments/README.md` and the agent knows them from `AGENTS.md`
- The prompt that starts every experiment, roughly: "Create `app/experiments/w1/<name>` with a full-screen canvas that ..." Then look at localhost:3000/experiments/w1/name and talk to it
- A variant is a new folder (`mouse-trail-2`), not an edit. Finished experiments stay as a record
- After each experiment that works: `git add .` → `git commit -m "w1: <name>"`. Before a risky change: commit. When the agent breaks it: `git restore .`
- If you fall behind, don't catch up on the code. Catch up on the loop: ask the agent to build what you saw, in your words

## 9. GLSL

- What is <Term id="glsl" />?
  - OpenGL Shading Language: a small C-like language that runs on the GPU, not in Javascript
  - Your program runs once per vertex (vertex shader) and once per pixel (fragment shader), all of them in parallel
  - Fragment shader: given a pixel coordinate (and time, mouse, …), return a colour. That's it
  - Thousands of pixels at once → things that are too slow in a Canvas loop become free
- How does it connect to Three.js?
  - `ShaderMaterial`: a material whose vertex/fragment shaders you write yourself
  - `uniforms`: values you pass from Javascript into the shader every frame (time, mouse, resolution, …)
  - A single full-screen plane + a fragment shader = a 2D canvas painted by the GPU
- What is it good for?
  - Per-pixel fields: gradients, noise, flow, distance fields, blur, feedback
  - Large numbers of particles / instances
  - Post-processing: effects over the whole frame
- Not good for: layout, text, UI logic. Let React/CSS do that
- References
  - The Book of Shaders [LINK](https://thebookofshaders.com/)
  - Shadertoy [LINK](https://www.shadertoy.com/)
  - Three.js ShaderMaterial [LINK](https://threejs.org/docs/#api/en/materials/ShaderMaterial)

## 10. Three.js

- What is <Term id="threejs" />?
  - A Javascript 3D Library
  - 3D + Javascript, Web 3D, Open Source (Free!), Coding-based
  - Interactive, Accessible, Incorporable with pre-built 3D Models
  - Vanilla Three.js = Vanilla Javascript + Three.js
    - I.e. Not using React Three
    - Do-able but longer code, not bonded with React Logic
- What is React-Three?
  - Series of frameworks/integration strategy to use Three.js efficiently and in a React Way
  - **<Term id="r3f">React-Three Fiber</Term>:** React renderer for Three.js [LINK](https://r3f.docs.pmnd.rs/getting-started/introduction)
    - https://codesandbox.io/p/sandbox/5g22g7
  - **React-Three Drei:** Collection of Ready-to-use utilities/help functions [LINK](https://github.com/pmndrs/drei)
  - React-Three Postprocessing: Post-processing Effects [LINK](https://github.com/pmndrs/react-postprocessing)
  - React-Three Rapier/Cannon: Physics Library [LINK](https://github.com/pmndrs/react-three-rapier)
  - Not exactly a React-Three integration, but React Spring (Animation Library) [LINK](https://www.react-spring.dev/)
- Why Three.js?
  - Cinema 4D: Static 3D Moving Image, GUI-based, High Accessibility, Low Interactivity
  - Unity: Interactive 3D Game, GUI + C# Coding, Low Accessibility, High Interactivity
  - Three.js: Interactive web-based 3D environment, Javascript-based Coding, Mid Accessibility, Mid Interactivity
  - When to Use Three.js
    - Interactive Web
    - Integrated Web
    - Easy-to-access Demo (No Installation)
